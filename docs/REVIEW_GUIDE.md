# MilestoneBond reviewer guide

MilestoneBond is a standalone, test-only GenLayer app for staged software delivery. The current v0.5 release is on Bradbury; older v0.4 and v0.3 runs are on StudioNet. It is not audited or suitable for real-value escrow. The delivery policy is an explicitly **sponsor-approved, unmerged commit**—not a claim that code merged. The sponsor and author use distinct wallets; the author wallet is bound to a frozen GitHub account and exact PR-body claim. Validators independently re-fetch the public source and compare criterion verdicts before a tranche can be credited.

## Current v0.5 Bradbury recovery release

Start at the [live app](https://demigodd00.github.io/milestonebond/) and its Bradbury proof panel. The [v0.5 contract](https://explorer-bradbury.genlayer.com/address/0xf7358a08822cbc439a83225b8cf48f21b10468dc), [deployment record](../deployments/bradbury_v0.5.json), [readable source](../contracts/milestone_bond_v0_5.py), [reproducible packed wrapper](../contracts/milestone_bond_v0_5_packed.py), and [dated live verification JSON](../public/verification-v0.5.json) bind the source and policy to four finalized, successful transactions.

For the exact failure branch, compare the [funding](https://explorer-bradbury.genlayer.com/tx/0x9224a9882dd09fde5fb6e53564614d54ae01ea8ea6db06f6d474057039ba717d), [expiry recovery](https://explorer-bradbury.genlayer.com/tx/0x4011ed975b3c5693db80ee21bdf051750eba266d2176ad2fde564abccdec1749), [failed external withdrawal](https://explorer-bradbury.genlayer.com/tx/0xfe2ebc1e423c1713da68fcd56ee1d73be5a76a01b88ee33782482d3e8457b24b), its [EVM finalization and linked processor-failure event](https://explorer-bradbury.genlayer.com/tx/0x0f7707a97b218e655ac8a927fe94a832c31b66708db2d0a81d1070087d56e9a8), and the [reconciliation](https://explorer-bradbury.genlayer.com/tx/0x746ec103d9996ba283e93bd2bb424e816e9d50380459aee5f2aae12194f2ccd5). ## Start here — no wallet needed

1. [Open the app](https://demigodd00.github.io/milestonebond/). The hero diagram and walkthrough are illustrative. The archived v0.3 proof panel links to its actual transactions; the current **Live projects** tab reads Bradbury v0.5 only.
2. Inspect the [v0.3 contract](https://explorer-studio.genlayer.com/contracts/0xa3Cb18a9846a49aF882Cae38fB79923D7F6DcC34) and the archived v0.3 record for `MB-LIVE-002`; do not expect this historical project in the current v0.5 project list.
3. Read the [machine-readable verification record](../public/verification-v0.3.json) and [steward response](STEWARD_FIXES_V03.md). The former checks onchain source, frozen evidence hashes, each finalized receipt, the native child transfer, and final accounting. It records one deliberately failed pre-approval review and one deliberately failed wrong-parent reconciliation as failures, not as successful steps.
4. Inspect [issue #1](https://github.com/Demigodd00/milestonebond/issues/1), [PR #2](https://github.com/Demigodd00/milestonebond/pull/2), [PR #3](https://github.com/Demigodd00/milestonebond/pull/3), and their fresh [stage-one](https://github.com/Demigodd00/milestonebond/actions/runs/38197462942/attempts/2) and [stage-two](https://github.com/Demigodd00/milestonebond/actions/runs/38198377989/attempts/2) CI attempts. Check the exact `MilestoneBond-Claim` lines and the onchain sponsor approvals before interpreting the validator verdicts.
5. Compare the [withdrawal parent](https://explorer-studio.genlayer.com/transactions/0x2eb73e68d42db8fc74a2f5e44372f0dd86da65a5d23d6ceeffb88c96ac6faac6), [triggered native child](https://explorer-studio.genlayer.com/transactions/0xf8d01660e706e44d976cedc5c612156d8dd3a6f0307ff802aa3ab6e67f6c14bc), [wrong-parent rejection](https://explorer-studio.genlayer.com/transactions/0x266314bedf989710d5412a7b807a2eb716947dc7d7fbe4f91bf30349e55ea726), and [correct reconciliation](https://explorer-studio.genlayer.com/transactions/0x09c68d91a3800464fec4cdf55d2384c92cc805f0044e31ce04d6d8f81baa9c6a). The child must be finalized with `value_credited=true`; the final accounting shows one 0.002 test-GEN payout and zero pending entitlement.

The [contract source](../contracts/milestone_bond.py), [33 direct tests](../tests/direct/test_steward_protections.py), [architecture](ARCHITECTURE.md), and [security limitations](SECURITY.md) are in this dedicated repository. The v0.3 deployed source SHA-256 and exact runner dependency are pinned in [the deployment record](../deployments/studionet_v0.3.json). A challenge-window `ACCEPTED` verdict alone is not a payout; the separate finalization must succeed.

## Historical run and boundaries

The earlier [v0.2 timeline](LIVE_DEMO.md), [v0.2 contract](https://explorer-studio.genlayer.com/contracts/0xb437593b7656254226ce496bc6f9A052A11D6345), and [archived verification JSON](../public/verification-v0.2.json) remain available. They are **not** evidence that the v0.3 sponsor, GitHub-author, or withdrawal-reconciliation protections existed in v0.2.

The direct adversarial tests mock GitHub, LLM and RPC data; they cannot reproduce a failed protocol child transfer. The historical v0.3 happy-path child and negative parent-hash probe are finalized on StudioNet, but do not prove recovery after a real failed external transfer. [Isolated internal-message probes](FAILED_TRANSFER_BOUNDARY.md) further show that execution failure is not equivalent to `value_credited=false`. The separate v0.5 Bradbury run above closes the external-rejection gap, but does not prove live reserve consumption after an unreturned loss. Ambiguous transfers remain pending rather than allowing automatic duplicate payout. GitHub account association, CI runner/dependencies, GenLayer and EVM RPCs, validator availability, and sponsor-authored criteria remain external trust dependencies. A dated verification JSON is historical if a testnet resets.

## Try the signing path

Use a test-only EIP-1193 browser wallet on Bradbury, chain ID `4221`, funded with test GEN through the [testnet faucet](https://testnet-faucet.genlayer.foundation/). The site checks the verified v0.5 address, onchain config, source hash and Bradbury ghost code before signing. The author must put the displayed exact claim in an open, unmerged PR, submit a fresh passing CI attempt, then wait for separate sponsor approval, validator review and challenge-window finalization. Withdrawals require a separate exact EVM-finalization reconciliation. The public demo needs no wallet or funding to inspect.
